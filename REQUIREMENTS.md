# Requirements

> This is the project-level requirements index and summary. Add detailed records under `requirements/` when the set grows.

## Requirement Authoring

Write each requirement so it is clear, singular, feasible, and verifiable. Prefer a measurable threshold and a defined operating condition. Avoid embedding a particular design solution unless it is a genuine constraint.

Use stable identifiers (for example, `SYS-001`, `ELEC-001`, `SW-001`). Do not reuse identifiers after retirement. Record rationale and verification method, and link derived requirements to their parent.

## Quality Checks

- Each requirement has a unique, stable ID.
- Each statement expresses one obligation and has an observable pass/fail condition.
- Units, tolerances, environmental conditions, and measurement points are specified where applicable.
- Conflicts, dependencies, assumptions, and rationale are recorded.
- Every approved requirement has an owner and a planned verification method.
- Changes are reviewed for impact on architecture, design, risk, sourcing, regulatory obligations, and verification.
